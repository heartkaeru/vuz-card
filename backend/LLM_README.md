# Модуль извлечения фактов и подготовки материалов

Это основная точка входа в документацию LLM для разработчиков парсера и backend.
Команды ниже выполняются из `backend`, если явно не указано иное.

Для защиты 7 ноября начните с [запуска Демо 1](../docs/DEMO1_RUNBOOK.md).
Подключены парсер, GigaChat, SQLite, проверка в интерфейсе и экспорт PPTX/Markdown.
Подробности: [LLMWorkflow и CLI](docs/llm/LLM_WORKFLOW.md),
[шаблон по примерам заказчика](templates/README.md),
[проверка интеграции](reports/demo1_integration_2026-11-04.md).

2. Передайте документы парсера в `AssistantPipeline.extract_facts()`.
3. Сохраните кандидатов и доказательства на сервере, организуйте принятие сотрудником.
4. Передайте принятые факты в `generate_materials()`. Полученные справка и тезисы —
   черновик; сборку файла `.pptx` выполняет отдельный модуль документов.

читать их все для первого подключения не требуется. Целевые требования и предложения
в [спецификации](../SPECIFICATION.md) шире текущей реализации этого модуля.

## Обзор модуля

Первая реализация задачи AI/LLM Engineer. Python 3.11+. Публичные интерфейсы:
`AssistantPipeline.extract_facts()` и `AssistantPipeline.generate_materials()`.
Контракты имеют `schema_version="0.1"`; это реализация части предложенных
[требований](../SPECIFICATION.md#технические-требования-к-ии-помощнику-карточка-вуза), а не всего MVP и не отчёт о достигнутых метриках.

Дополнительно доступен [контракт 0.2: фрагменты и владельцы контактов](docs/llm/LLM_FRAGMENTS.md).
Он включается явно через `schema_version="0.2"`; старый режим остаётся доступным.

Для профиля, проектов и событий добавлен отдельный
[контракт 0.3](docs/llm/LLM_CONTEXT.md) и смешанная справка по принятым фактам.
[План LLM-части MVP и конкретные зависимости от команды](docs/llm/MVP_LLM_PLAN.md).

Первый запрос пользователя разбирает отдельный
[`RequestInterpreter`](docs/llm/LLM_REQUESTS.md): название/город/URL, нужные материалы и
следующий шаг или уточняющий вопрос. Поиск, чат и создание карточки он не выполняет.

## Что сделано

- Адаптер GigaChat SDK: структурированный JSON-ответ, тайм-аут, ограниченные повторы SDK,
  обработка ошибок, отказ от усечённых ответов; проверка TLS включена.
- Извлечение ФИО, должностей, статуса назначения, персональных рабочих контактов,
  подразделений, зон ответственности, образования, степени и этапов карьеры.
- Атомарные кандидаты с цитатами; URL, даты и хеш исходного текста добавляет сервис.
- Проверка схемы, принадлежности `source_id`, дословного наличия цитаты и ряда значений,
  наличия имени владельца в цитате, формата контактов. Ошибочные кандидаты сохраняются
  как `rejected` с причинами; валидные — `pending`, а не `verified`.
- Разбиение текста с перекрытием, исходными смещениями и ограничением числа фрагментов.
  Частичные ошибки и необработанные фрагменты не скрываются за полным успехом.
- Консервативные отметки возможных конфликтов должностей и нескольких руководителей.
- Генерация структуры справки и тезисов слайдов по принятым фактам; JSON и Markdown
  с реестром источников. Результат всегда `draft`.
- В режиме 0.2/0.3 утверждения только о ФИО, должностях, статусах и подразделениях
  формируются из точных принятых значений: пересказ модели не добавляет статус и. о.
  или факт назначения. Смешанные утверждения по-прежнему требуют смысловой проверки.
- Офлайн-пример и тесты без ключа/API.

## Установка в PowerShell

Из корня репозитория:

```powershell
py -3.11 -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements-dev.txt
Set-Location backend
```

Если нужен только модуль без FastAPI и генератора PPTX, достаточно
`requirements-llm.txt`; для тестов дополнительно нужен `pytest==8.4.2`.

## Демонстрация без API

Из `backend`:

```powershell
.venv/Scripts/python.exe -m examples.llm.demo
```

Создаются `output/demo/facts.json`, `draft.json` и `brief.md`. Это вымышленный вуз и
заранее сохранённые ответы; обращения к модели нет. Для демонстрации второго этапа
проверка сотрудником **имитируется только в примере**, а исходные факты в `facts.json`
остаются `pending`. Демонстрация не измеряет точность GigaChat.

Отдельный запуск извлечения с воспроизведением ответа:

```powershell
.venv/Scripts/python.exe -m app.services.llm extract --input examples/llm/extract_request.json --responses examples/llm/extract_responses.json --output output/facts.json
```

Флаг `--responses` явно включает офлайн-режим. Без него всегда используется GigaChat;
при отсутствии доступа сервис не подменяет результат тестовыми данными.

## Реальный запуск GigaChat

```powershell
Copy-Item .env.example .env
```

Заполнить локально `GIGACHAT_CREDENTIALS`, `GIGACHAT_MODEL`, `GIGACHAT_SCOPE` для
доступного аккаунта. Ключ не помещать в Git и не пересылать в чат. Модель и scope не
заданы по умолчанию: их доступность зависит от аккаунта. При необходимости настроить
`GIGACHAT_BASE_URL` и `GIGACHAT_CA_BUNDLE_FILE` с доверенными сертификатами.
При `gigachat_certificate_verification_failed` нужен сертификат из
[официальной инструкции](https://developers.sber.ru/docs/ru/gigachat/certificates).
Для текущего локального окружения создан объединённый PEM-файл (стандартные CA
`certifi` плюс официальный корневой сертификат Минцифры) в
`output/certs/gigachat-ca.pem`; его абсолютный путь указан только в локальном `.env`.
Файл и ключ не входят в Git. После переноса проекта или удаления `output/certs`
сертификат нужно настроить заново. Проверка TLS остаётся включённой; хранилище
сертификатов ОС не изменяется.
В CLI `.env` загружается только при явном `--env-file`; `run.py` явно загружает
`backend/.env`. Существующие переменные окружения
имеют приоритет. Установленный SDK зафиксирован в `requirements-llm.txt`.

Подготовить JSON с реальными текстами по схеме `ExtractionRequest` (образец —
`examples/llm/extract_request.json`). Даты должны включать часовой пояс, `source_id`
уникален. Использовать тексты парсера, а не придуманное моделью описание сайта.

```powershell
.venv/Scripts/python.exe -m app.services.llm extract --env-file .env --input output/request.json --output output/facts.json
```

Результат содержит факты, пробелы по доступным текстам, ошибки по фрагментам и
метаданные запуска. `complete=true` означает успешную обработку переданных фрагментов
и автоматические проверки, а не полноту информации в интернете или принятие человеком.
Конфликты нужно смотреть в статусах фактов отдельно.

Для генерации сотрудник сверяет цитаты, владельцев, исторический контекст и актуальность.
Доверенный сервер формирует `GenerationRequest`: организация и версия карточки,
`facts`, `meeting`. В прототипе этот JSON можно подготовить вручную после проверки.
Для каждого принятого факта нужны `verification_status="verified"`, `reviewed_by`,
`reviewed_at`, `last_checked_at`, `freshness_status="within_window"`; ошибки и конфликты
сначала разрешаются. Даты проверки должны быть с часовым поясом и не из будущего.
В первой версии перед встречей требуется проверка не старше 7 дней для всех выбранных
фактов; окно задаётся `review_window_days` при создании пайплайна.

```powershell
.venv/Scripts/python.exe -m app.services.llm draft --env-file .env --input output/reviewed_request.json --output output/draft.json --markdown output/brief.md
```

`reviewed_request.json` — это не весь `ExtractionResult`: оставить `institution`,
массив проверенных `facts`, добавить `meeting` с целью и необязательной датой;
`schema_version` — `0.1`. Не переносить поля `run`, `gaps`, `errors`, `complete`.
Не менять статусы автоматически только для обхода проверки.

Коды завершения: 0 — результат сформирован; 1 — проблема конфигурации/входного файла;
2 — частичная обработка, ошибка модели либо отказ проверки материалов. При частичном
извлечении JSON с причинами сохраняется. CLI не печатает тела ответов API, ключи и
полный текст ошибок валидации, который может содержать исходные данные.
Безопасные коды ошибок API различают HTTP-статус (`gigachat_http_401` и т. п.),
тайм-аут, сбой соединения и ошибку проверки сертификата, не раскрывая заголовки и тело ответа.

## Подключение к серверу

```python
from app.services.llm import AssistantPipeline
from app.services.llm.client import GigaChatProvider, GigaChatSettings
from app.services.llm.models import ExtractionRequest

pipeline = AssistantPipeline(GigaChatProvider(GigaChatSettings.from_env()))
request = ExtractionRequest.model_validate(parser_result)
candidates = await pipeline.extract_facts(request)
```

`parser_result` должен соответствовать контракту. Сам `AssistantPipeline` не пишет в БД;
хранение входа, кандидатов и решений реализует `LLMWorkflow`. Рабочий HTTP-сценарий
`/api/v1/ai` использует его вместе с `DemoRepository`; принятые факты передаются
генератору и сохраняются отдельным неизменяемым снимком материала.
Старый `run_refresh_pipeline` остаётся имитацией в deprecated API.
Автоматического принятия фактов нет: review принимает только ID факта и решение,
а сервер сам выставляет статусы/время после проверки условий. Ручное имя проверяющего
локального прототипа пока не связано с учётной записью.

Публичные HTTP-эндпоинты для загрузки готовых «проверенных» фактов не добавлены. Проверка
метаданных решения в библиотеке не является авторизацией: при подключении сервер
обязан сам устанавливать автора решения, проверять права, версию карточки и читать
принятые факты из доверенного хранилища, а не принимать эти статусы от браузера.

## Проверки и ограничения

```powershell
.venv/Scripts/python.exe -m pytest -q
```

Тесты проверяют приложение и контракт SDK на подменённых ответах; они не доказывают
качество модели или устойчивость к любым инструкциям внутри сайтов. 31 октября 2026
выполнен первый реальный запрос к `GigaChat-2-Pro` на синтетическом тексте примера:
модель вернула три кандидата, один прошёл автоматические проверки (должность и. о.),
два отклонены. Телефон приёмной был ошибочно приписан человеку и отфильтрован;
email отклонён из-за дословного сопоставления ФИО в разных падежах. Это описание первого
прогона до доработки. Затем проведён пилот на реальных официальных страницах трёх
организаций: [результаты и ограничения](reports/llm_pilot_2026-10-31.md). Он служил для
отладки; независимая контрольная оценка на 10–20 организациях пока не выполнена.

Автоматическая проверка цитаты и имени не доказывает смысловую связь человека с контактом
или должностью. Для полных ФИО поддержаны регистр, ё/е и словарные падежные формы
через `pymorphy3`: должны совпасть фамилия, имя и отчество в одном падеже и роде.
Инициалы, перестановки, опечатки, неизвестные словарю формы и варианты вроде
«Наталья/Наталия» автоматически не отождествляются. Полноценное сопоставление лиц,
исторических назначений, филиалов и автоматическое разрешение конфликтов не реализованы.
Кандидаты не объединяются в единую запись человека только по ФИО; дедупликация ограничена
одинаковыми предложениями из одного источника, межисточниковое объединение — дальнейшая работа.

Поле `ExtractionRequest.fields` необязательно: можно ограничить набор извлекаемых
полей (например, ФИО/должности/контакты). Незаданные поля по умолчанию не ограничены.
Если модель уже выделила полное ФИО в `subject`, но пропустила отдельный `person.name`,
сервис создаёт такой кандидат только из автоматически валидированного факта с цитатой.
Происхождение отмечается `origin="subject_projection"`; статус остаётся `pending`.

В черновике проверяются известность `fact_ids`, числовые фрагменты относительно значений
цитируемых фактов, объём справки и число тезисов. Семантическая проверка всех перефразировок,
новых имён и выводов остаётся за сотрудником. Ссылка на правильный ID сама по себе не
делает весь текст утверждения достоверным. Название учреждения и контекст встречи берутся
из входа сервера. Результат нельзя выдавать за готовый проверенный материал без просмотра.
Полные цитаты не передаются генератору: они могут содержать ещё не принятые сведения.
Модель получает только ID, имя владельца, поле и значение принятого факта. Реестр
источников строится сервисом. Модель видит короткие ссылки с enum в JSON-схеме;
сервис восстанавливает исходные ID. Скобочная аннотация уже перечисленных в `fact_ids`
ID удаляется как форматирование; неизвестные ID и ID внутри обычной фразы блокируются.

Сам `AssistantPipeline` не выполняет веб-поиск, загрузку сайтов, OCR или матчинг продуктов.
Режим 0.3 извлекает проекты/мероприятия из переданных текстов, но требует отдельной оценки.
В сценарии Демо 1 загрузку выполняет парсер, исходные снимки сохраняет `LLMRepository`,
PPTX собирает `meeting_card_pptx.py`. Хеш позволяет проверить версию текста, но не заменяет снимок.
Реестр источников и границы фрагментов сохраняются в JSON и Markdown. Порог числа фрагментов
ограничивает расходы; символьное разбиение ещё не является точным подсчётом токенов модели.

## Как менять требования

- Поля и ограничения — `app/services/llm/models.py`.
- Промпты — `app/services/llm/prompts/*.txt`; при изменении обновлять версию в инструкции
  и `run_info` соответствующего этапа, затем повторять контрольную оценку.
- Провайдер API — `client.py`, интерфейс `JSONProvider` позволяет заменить его независимо.
- Проверки, разбиение и предвстречное окно — `pipeline.py`.
- Сопоставление полных ФИО в цитате — `names.py`; оно не объединяет записи людей в CRM.
- Отображение справки — `render.py`; внешний шаблон PPTX остаётся отдельным компонентом.

Ломающие изменения контракта требуют новой `schema_version` и согласования с парсером,
сервером и БД. Изменение промпта не требует переписывать приложение, но может изменить
качество извлечения и потому требует повторной проверки.

Официальные источники по API:
[Python SDK](https://developers.sber.ru/docs/ru/gigachat/guides/using-sdks),
[структурированный вывод](https://developers.sber.ru/docs/ru/gigachat/guides/structured-output).

## Повторение пилота

Из `backend` установить `requirements-pilot.txt`. Он добавляет BeautifulSoup для
чтения сохранённых HTML; производственный LLM-модуль от него не зависит.

```powershell
.venv/Scripts/python.exe -m pip install -r requirements-pilot.txt
.venv/Scripts/python.exe -u -m examples.llm.pilot fetch --manifest output/pilot/manifest.json
.venv/Scripts/python.exe -u -m examples.llm.pilot extract --manifest output/pilot/manifest.json
.venv/Scripts/python.exe -m examples.llm.evaluate output/pilot
.venv/Scripts/python.exe -u -m examples.llm.pilot draft --manifest output/pilot/manifest.json
```

Локальный `manifest.json` содержит выбранные организации, публичные URL, HTML-селекторы
и границы исследуемых фрагментов. `gold.json` задаёт эталон и область подсчёта метрик
до запросов к модели. Они вместе со снимками остаются в игнорируемой папке `output/pilot`;
для другого окружения их нужно подготовить отдельно, а не ожидать загрузки из Git.
Исходный Excel не изменяется и не отправляется в API: из него использованы только
названия для выбора организаций. Повторный `fetch` использует сохранённые снимки;
`--refresh` явно обновляет их. Метаданные содержат время получения и SHA-256.

Перед `draft` требуется `reviewed-request.json` для каждого случая. В выполненном
техническом пилоте проверку фактов по снимкам провёл ассистент, а принятие сотрудником
CRM явно имитировалось и зафиксировано в `review-decisions.json`. Это не подтверждение
сотрудника и не запись в CRM. В рабочем процессе решение принимает уполномоченный
пользователь. Результаты пилота остаются черновиками.

Запросы выполняются последовательно. Для пилота установлен тайм-аут 180 секунд без
автоповторов и максимум 8192 токена ответа; штатные настройки `.env` не меняются.
`--case isu` позволяет выполнить один случай. Контент ответов модели сохраняется
для разбора ошибок; заголовки SDK, токены и credentials в эти файлы не записываются.
Флаг `--replay` повторно обрабатывает уже сохранённые реальные ответы без нового
запроса; результат помечается `provider=gigachat-recording`. Это удобно для проверки
валидаторов и форматирования, но не заменяет измерение качества новой версии промпта.
