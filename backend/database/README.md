# Локальная база ВУЗ-CRM и первичный импорт

Реализован самостоятельный модуль БД и загрузки, без интерфейса CRM и веб-парсера. Это локальная SQLite-реализация подготовленной логической структуры. Выбор промышленной CRM/СУБД не изменён: при интеграции потребуются адаптер и миграции на выбранную платформу.

## Что создано

- `schema.py` — схема, ограничения и начальные справочники; версия хранится в PRAGMA user_version. Инициализация транзакционная, повторный запуск сохраняет данные.
- `intake.py` — чтение Excel, исходные строки, нормализация для поиска, реестр кандидатов, журнал применения и очередь проверки.
- `review.py` — приём подтверждённых сопоставлений по ИНН, отчёт и CSV-реестры.
- `__main__.py` — локальные административные команды.
- `tests/test_database.py` — проверки на синтетических данных; фиктивные ИНН используются только внутри временных тестовых баз.

Схема включает юридические лица, учреждения/подразделения, варианты названий, контактные точки, людей, назначения, каналы, ФОТ, договоры/стороны, встречи/участников и договорённости. Источники, партии, наблюдения и аудит хранятся отдельно. `registry_candidate` и `identity_resolution` — физические дополнения для безопасного первичного сведения.

Пока импортируется только контактный реестр. Таблицы ФОТ, договоров и встреч созданы, но их Excel-маппинги требуют реальных образцов и согласования методик. Заполненные ФИО и телефоны сохраняются в staging, без автоматического создания людей и сомнительной нормализации. Смешанные должности/ФИО не разбираются догадкой. Любые неизвестные колонки остаются в исходном JSON.

## Требования и запуск

Python 3.11+ и зависимости из `backend/requirements.txt`. Выполнять команды из корня репозитория `vuz-card`:

```powershell
python -m pip install -r backend/requirements.txt
python -m backend.database --db ../data_work/vuz_card.sqlite3 init
python -m backend.database --db ../data_work/vuz_card.sqlite3 import "../material1/Копия ББ_2025_26 уч год_кейс.xlsx" --department "Отдел не подтверждён"
python -m backend.database --db ../data_work/vuz_card.sqlite3 report --output ../data_work/reports
python -m unittest discover -s tests -v
```

Команда import принимает несколько файлов:

```powershell
python -m backend.database --db ../data_work/vuz_card.sqlite3 import ../incoming/department1.xlsx ../incoming/department2.xlsx --department "Общий источник"
```

Для указания разных отделов вызывать импорт отдельно для каждого отдела. Поддерживаются `.xlsx` и `.xlsm`. Старый `.xls` нужно явно преобразовать; макросы не выполняются. Заголовок ищется в первых 30 строках: название учреждения и регион либо ИНН. Поддерживаемые названия колонок перечислены в HEADERS в intake.py. Неизвестный шаблон целиком отклоняется; неизвестный лист внутри распознанного файла сохраняется как неподдержанный, без применения.

**В каталоге репозитория запрещено создавать реальную БД и отчёты командой CLI.** Они должны лежать, например, в `project_vuz_card/data_work`. `.gitignore` дополнительно исключает SQLite, кэш Python и окружение. Данные источников, очередь проверки и заполненный identity mapping не коммитить.

## Что происходит при импорте

1. Считываются байты файла, вычисляется SHA-256. Парсится именно это содержимое.
2. Сохраняются исходные непустые строки: адреса ячеек, значение, тип и формат. Повтор того же файла с другим именем не создаёт новые source_record.
3. Формируется новая аудируемая партия. Строки без названия остаются без учреждения; значение из предыдущей строки не переносится.
4. Названия группируются только по точному нормализованному имени и региону. Это предварительные группы, не юридически подтверждённые карточки. Разные названия могут быть связаны с одной карточкой только через проверенный mapping.
5. Наличие ИНН в Excel проверяется, но не считается автоматическим подтверждением принадлежности. Для принятия требуется identity mapping. Противоречие его ИНН значению Excel блокирует применение.
6. После подтверждения учреждения создаются контактные точки и извлечённые email со статусом pending. Подтверждение учреждения не подтверждает актуальность контактов.
7. Для каждого применения сохраняются происхождение и журнал. Повтор не создаёт те же контакты или каналы заново. История партий staging намеренно накапливается.

Статус applied означает, что привязка учреждения и поддержанные части строки применены. Другие значения строки всё ещё могут требовать проверки. completed_with_review означает завершение технической загрузки, а не завершение очистки данных. Формулы сохраняются в сырье и блокируют применение строки; их значения не вычисляются библиотекой.

## Подтверждение ИНН и подразделений

Сначала загрузить Excel, затем создать JSON со списком проверенных соответствий. В репозитории `identity_mapping.example.json` содержит пустой список, без выдуманных реквизитов.

Обязательные поля одной записи:

| Поле | Смысл |
|---|---|
| source_name | Точное название-кандидат из Excel |
| source_region | Регион-кандидат из Excel; сопоставление после нормализации пробелов/регистра |
| inn | Проверенный 10-значный ИНН строкой |
| official_name | Подтверждённое полное название юридического лица |
| unit_code | Согласованный стабильный код головной организации или подразделения |
| unit_type | head / branch / college / other |
| verified_by | Кто подтвердил соответствие |
| verified_at | ISO-время с часовым поясом, например 2026-11-02T12:00:00+05:00 |
| evidence | Ссылка на официальный источник или реквизиты подтверждающего документа |

Дополнительно: display_name, education_type (university/spo/mixed/unknown), kpp. Для нескольких названий одной организации задаётся одинаковый ИНН и unit_code. Для филиалов с общим ИНН — разные unit_code. ИНН и ФИО не заменяют внутренние ID.

Mapping является утверждением ответственного проверяющего; модуль проверяет контрольный разряд, формат и противоречия, но не обращается самостоятельно в ФНС и не проверяет истинность введённой ссылки. Сопоставление с уже другой карточкой отклоняется; произвольной перезаписи истории нет. Копия JSON-полей сохраняется в source_record, поэтому решение воспроизводимо даже после изменения файла mapping.

В `data_work/identity_mapping.todo.json` сформирован список реальных кандидатов с незаполненными подтверждениями. Для resolve нужно передавать только полностью проверенные записи, а не весь незаполненный список.

```powershell
python -m backend.database --db ../data_work/vuz_card.sqlite3 resolve ../data_work/verified_identities.json
python -m backend.database --db ../data_work/vuz_card.sqlite3 import "../material1/Копия ББ_2025_26 уч год_кейс.xlsx" --department "Отдел не подтверждён"
python -m backend.database --db ../data_work/vuz_card.sqlite3 report --output ../data_work/reports
```

У существующих полей не выполняется автоматическое обновление: непустое противоречащее значение отправляется на проверку. Полноценное редактирование с optimistic locking и API CRM не реализовано; здесь административное первичное наполнение. Ранее зарегистрированные проблемы остаются в истории, текущая очередь и агрегаты отчёта строятся по последней попытке обработки каждой исходной строки.

## Точность и ограничения физической модели

SQLite не обеспечивает fixed-point DECIMAL тем же способом, что серверные СУБД. Поэтому:

- amount_minor — денежная сумма в сотых долях валюты, INTEGER, например 12345 = 123,45;
- count_10000 — численность с масштабом 10 000;
- ratio_100000000 — доля с масштабом 100 000 000;
- валюта обязательна для денежных сумм, отсутствует для численности и долей;
- значения ограничены диапазоном 64-битного INTEGER; большие суммы требуют серверной DECIMAL-модели;
- сумма основного договора и допсоглашения не агрегируется автоматически.

Финансовые таблицы пока заполняются только через будущие согласованные преобразования, не через контактный импорт. Прямой ввод денежных REAL/float не применяется.

Пользователи/роли будущей CRM представлены внешними текстовыми ID, без второй системы авторизации. Идентичность подразделений и родительские циклы контролируются БД. Связи и ограничения суммы/периметра заданы; проверки публикации (минимум две стороны договора, согласованность участника и назначения, актуальность источников) должны быть добавлены в серверный слой перед интеграцией с рабочей CRM. Локальный модуль не является сервером с разграничением доступа.

## Выходные файлы

- `vuz_card.sqlite3` — база; можно открыть SQLite-клиентом для просмотра.
- `reports/registry_candidates.csv` — единый предварительный список названий с количеством исходных строк/файлов и статусом идентификации.
- `reports/accepted_registry.csv` — только карточки с подтверждённым ИНН.
- `reports/review_queue.csv` — строки, требующие проверки, с происхождением и кодами причин; актуальная попытка для каждой исходной строки.
- `reports/import_report.json` и `reports/IMPORT_REPORT.md` — технические итоги и ограничения.

CSV содержат исходные сведения и создаются вне репозитория. Потенциальные формулы в экспортируемом тексте экранируются при открытии в Excel. Значения в БД остаются неизменными.
