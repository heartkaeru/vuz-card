# PostgreSQL / Supabase: схема и перенос первой итерации

## Что готово и что ещё требуется

| Часть | Состояние |
|---|---|
| Реляционная схема, ограничения, версии и аудит | Реализованы в двух SQL-миграциях; проверены на PostgreSQL 18 |
| Перенос эталонных файлов первой итерации | Реализован и проверен локально: 10 записей → 8 уникальных вузов |
| Облачный проект Supabase | Создан пользователем; подключение проверено 20.11.2026 |
| Миграции и данные в облаке | Применены обе миграции, загружены 8 демонстрационных вузов; проверены связи и RLS |
| Доступ команды к Supabase Studio | Требуются аккаунт владельца и адреса участников; приглашения не отправлялись |
| Реестр карточек в основном AI API | Использует `DATABASE_URL` и `public.vuz_universities`; LLM-задания, чаты, проверки и отчёты пока хранятся в SQLite |

Данный модуль добавлен рядом с SQLite, без изменения её схемы, данных и интерфейсов. UUID новых записей и прежние идентификаторы связаны через vuz_import_records. Автоматическое переключение приложения требует отдельного адаптера.

## Структура

- `supabase/migrations/202611200001_vuz_schema.sql` — предметные таблицы, ограничения, индексы и справочник метрик.
- `supabase/migrations/202611200002_vuz_audit_and_access.sql` — версии, аудит, RLS и права Data API.
- `backend/database/postgres/db.py` — транзакционный мигратор с контрольными суммами и блокировкой от одновременного запуска.
- `legacy.py` — чтение исходных Python-литералов через AST без выполнения кода; план сведения; точный разбор сумм.
- `transfer.py` — перенос, сохранение исходных полей, проверка существующих записей и целостности.
- `__main__.py` — команды plan / migrate / seed / validate.
- `tests/test_postgres_migration.py` — 20 проверок; интеграционные тесты работают только с одноразовыми локальными базами.

Связи защищены FK; удаление используемых записей ограничено. Ключевые справочники не сливаются с карточкой в одну строку. Юрлицо может объединять несколько карточек подразделений; неподтверждённый ИНН хранится как reported_inn, без создания ложного legal_entity.

Уникальность карточек обеспечивается name_key: регистр, пробелы, ё/е и кавычки нормализуются. Одинаковое имя с противоречащим городом, сайтом или ИНН останавливает перенос, а не сливается автоматически. Для одноимённых филиалов нужны уточнённые названия карточек. Повтор имени должностного лица в другом вузе не делает его той же персоной.

## Какие данные переносятся

По умолчанию читаются только буквальные данные из:

1. `backend/seed.py`: список UNIVERSITIES — 7 карточек с названием, городом и сайтом.
2. `backend/app/data/mock_universities.py`: MOCK_UNIVERSITIES_DB — 3 старые демонстрационные карточки с руководителями, контактами и показателями.

Две записи совпадают по нормализованному полному названию и согласующимся реквизитам. Результат: 8 вузов, 6 руководителей, 12 каналов связи, 6 метрик и 7 проектов. Все 10 исходных записей сохраняются целиком. Неизвестные поля не теряются.

Это демонстрационные сведения, а не независимо проверенная информация о вузах. Поэтому is_demo=true, verification_status=needs_review. Исходное verified сохраняется в сырье и не превращается в подтверждение актуальности. ИНН из mock не повышается до проверенного юридического реквизита.

ФОТ «4.8 млрд руб.» переносится точным numeric 4800000000. Но период и методика не придуманы: period_start/period_end остаются NULL, методика и периметр unknown, использовать такой показатель как проверенный нельзя. contracts_count — заявленное число, а не повод создать 14 вымышленных договоров. Приём, инфраструктура, договоры, встречи и продуктовые рекомендации остаются пустыми, если их нет в источнике. Программа «Приоритет-2030» сама по себе не считается проектом со Сбером.

Excel из material1 и прежняя SQLite с 45 кандидатами не являются частью этого автоматического набора. Они сохраняются без изменений и требуют отдельного подтверждения сопоставлений. Новый перенос не объявляет эти 45 кандидатов юридически проверенными вузами.

Дополнительный вход: JSON-массив карточек с полями name, city, website и, при наличии, inn, short_name, region, officials, fot_volume, contracts_count, active_projects. Передаётся через повторяемый `--input`. Он также переносится как непроверенный демонстрационный источник. Прочие форматы без явного маппинга не исполняются.

## Создание проекта и подключение с другого компьютера

1. Войти в Supabase Dashboard под аккаунтом владельца команды.
2. Выбрать организацию и создать проект `vuz-card`, согласовав регион и доступный план. Пароль БД сохранить локально, не в репозитории.
3. Открыть Connect и скопировать Direct connection либо Session pooler. Для IPv4-сети без прямого IPv6 использовать выданную Session pooler строку; хост не вычислять по названию региона. Для миграций нужен PostgreSQL DSN, а не publishable key/service-role API key. [Подключение к PostgreSQL](https://supabase.com/docs/guides/database/connecting-to-postgres).
4. Создать вне репозитория файл `project_vuz_card/data_work/supabase/.env`:

```dotenv
DATABASE_URL=postgresql://postgres.PROJECT_REF:URL_ENCODED_PASSWORD@POOLER_HOST:5432/postgres?sslmode=require
```

Это шаблон, не готовая строка: точные имя пользователя и хост брать из Connect. Для Direct connection они отличаются. Не передавать пароль через аргументы команд или чат.

5. На компьютере запуска установить Python 3.11+ и зависимости модуля:

```powershell
cd F:\project_vuz_card\vuz-card
python -m pip install -r backend/requirements-postgres.txt
```

6. Подготовить план без подключения к БД:

```powershell
python -m backend.database.postgres plan --report ../data_work/supabase/transfer_plan.json
```

7. Проверить целевой проект в строке Connect и выполнить:

```powershell
python -m backend.database.postgres --env-file ../data_work/supabase/.env migrate
python -m backend.database.postgres --env-file ../data_work/supabase/.env seed --report ../data_work/supabase/import_report.json
python -m backend.database.postgres --env-file ../data_work/supabase/.env validate
```

8. Повторить seed: значения inserted должны быть нулевыми; не должны вырасти количество вузов, руководителей и записей аудита. История запусков при этом сохраняется.

Для JSON добавить `--input ../data_work/approved_source.json` в plan и seed. По умолчанию он дополняет два стандартных файла, а не заменяет их. На другом диске путь проекта может быть любым; команды выполняются из корня клонированного репозитория.

Миграции выполняются одной транзакцией с блокировкой. Контрольная сумма уже применённой миграции не должна меняться: дальнейшие изменения оформлять новым SQL-файлом. Не применять одновременно Python-мигратор и Supabase CLI migration push к одному набору без согласования истории миграций. SQL Editor подходит для просмотра/ручных запросов; после первичного развёртывания структуру менять через версии миграций.

## Доступ команды к Studio

Доступ к Dashboard и пользователи приложения — разные сущности.

1. Владелец открывает Organization → Team и приглашает конкретные email команды.
2. Для редактирования содержимого проекта использовать Developer; для управления аккаунтом/инфраструктурой — только необходимые роли Owner/Administrator.
3. Для просмотра использовать Read-Only, если доступен на выбранном плане. Согласно документации, Read-Only и project-scoped роли доступны на Team/Enterprise; нельзя обещать их наличие на бесплатном плане. Developer имеет более широкие права и не заменяет ограниченный просмотр. [Роли Supabase](https://supabase.com/docs/guides/platform/access-control).
4. После принятия приглашения проверить проект → Table Editor → public → таблицы vuz_*. Отдельно проверить чтение и изменение тестовой карточки.
5. Не выдавать всей команде один пароль postgres. При необходимости индивидуальных подключений использовать [сопоставление участников PostgreSQL-ролям](https://supabase.com/docs/guides/platform/team-database-access).

Для Data API роли viewer/editor/admin задаются в vuz_users. Нужен пользователь Supabase Auth и проверенный auth_subject. Начальное назначение выполняет владелец через SQL Editor, например:

```sql
INSERT INTO public.vuz_users(auth_subject,email,display_name,role)
SELECT id,email,'Имя участника','editor'
FROM auth.users WHERE email='member@example.com';
```

Email здесь пример; запрос нужно заменить на конкретного зарегистрированного участника. Клиентам не разрешено самостоятельно повышать роль. Анонимный доступ к таблицам закрыт, аудит нельзя править из Data API. Наличие приложения JWT из старого backend/auth не означает автоматическую совместимость с Supabase Auth — перенос авторизации не входит в данный модуль.

## Аудит и версии

В каждой изменяемой предметной таблице есть version, created_at/updated_at, created_by/updated_by. Триггер увеличивает версию при содержательном изменении; пустое обновление не создаёт шум в истории. Для optimistic locking сервер задаёт ожидаемую версию в той же транзакции:

```sql
BEGIN;
SELECT set_config('vuz.actor_type','human',true);
SELECT set_config('vuz.actor_label','Максим: ручная проверка',true);
-- При необходимости задать UUID зарегистрированного vuz_users:
-- SELECT set_config('vuz.actor_id','UUID_ПОЛЬЗОВАТЕЛЯ',true);
SELECT set_config('vuz.expected_version','1',true);
UPDATE public.vuz_universities SET city='Новый город' WHERE id='UUID_КАРТОЧКИ';
COMMIT;
```

ИИ-сервис задаёт actor_type=ai и понятный actor_label; импорт — migration. В Data API автор определяется через Supabase Auth subject. Для ручного SQL Editor с общей ролью postgres без контекста автором будет системная роль, а не вымышленный сотрудник. Чтобы знать конкретного человека, нужны отдельные подключения/проверенный actor_id; изменения через Table Editor не гарантируют имя коллеги в поле actor_id. Лог сохраняет database_role и время в любом случае.

Аудит защищён от UPDATE/DELETE; владелец БД обладает административными правами, поэтому журнал не является криптографически неизменяемым. Импорт не заменяет непустые ручные правки: при противоречии прерывается вся партия. Эти отличия от существующей записи нужно разрешать отдельно, сохраняя автора решения.

## Проверки

Для unit-проверок плана соединение не нужно. Интеграционные тесты запускаются только с отдельным LOCAL PostgreSQL admin-подключением и создают/удаляют базы vuz_test_<uuid>:

```powershell
$env:VUZ_TEST_DATABASE_URL='host=127.0.0.1 port=55439 user=vuz_verify dbname=postgres'
python -m unittest discover -s tests -p test_postgres_migration.py -v
```

На удалённом Supabase тесты намеренно не запускаются; проверка облака выполняется командами migrate/seed/validate. Для новой схемы проверены: FK и отсутствие осиротевших руководителей, уникальность имён, точность ФОТ, атомарность конфликтующего импорта, повтор без дублей, аудит human/ai, защита журнала, устаревшая версия, запрет анонимного доступа, отсутствие возможности самоповышения viewer.

Локальная проверка 20.11.2026: 20 тестов прошли; 8 вузов, 6 руководителей, 12 контактов, 6 метрик, 7 проектов; duplicate_names=0, orphan_officials=0, unvalidated_constraints=0. Эти результаты относятся к отдельной локальной PostgreSQL 18 базе, а не к облачному проекту.

## Подключение реестра к веб-приложению

Backend читает `DATABASE_URL` из окружения. При локальном запуске через `backend/run.py` также загружается корневой `.env`; ключи не передаются в Next.js и не должны иметь префикс `NEXT_PUBLIC_`. Нужна строка PostgreSQL из Dashboard → Connect (Direct connection либо Session pooler) с TLS.

Основной AI API показывает реестр из `public.vuz_universities`. Созданные из приложения карточки сохраняются как `is_demo=false`, `verification_status='ai_draft'` и попадают в аудит с типом актора `ai`. Таблицы и демонстрационные строки не перезаписываются. SQLite продолжает хранить AI-сборы, историю чата, проверки фактов и метаданные отчётов; эти рабочие данные пока не перенесены.

Строка подключения хранится вне репозитория: data_work/.env. Подключение требует TLS для удалённого сервера. Автоматическая подготовка запросов отключена для совместимости с Supabase pooler.

Повторный импорт сверяет существующие записи одним пакетным запросом в пределах исходников и выбранных вузов. Это сокращает сетевые обращения; сравнение всех переносимых полей и отказ от перезаписи ручных правок сохранены. Добавлена проверка ограниченного числа SQL-запросов при повторе.

Облачная повторная загрузка 20.11.2026 завершилась успешно: все значения inserted равны 0, число записей аудита осталось 604. Итоговый отчёт сохранён вне репозитория в data_work/supabase/cloud_repeat_import_report.json. Проверено: RLS включён на всех таблицах vuz_*, анонимный SELECT и клиентская правка ролей/аудита запрещены.
