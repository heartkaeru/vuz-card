# Разбор первого запроса пользователя

Реализован независимый модуль `RequestInterpreter`: первое сообщение → структурированное
задание. Он использует тот же адаптер GigaChat, что извлечение фактов. Это первый шаг
[сценария агента](../AGENT_WORKFLOW.md), а не реализация чата или поиска в интернете.

## Пример

Вход:

> Подготовь справку и презентацию о колледже Северный в городе N.
> Сайт: https://college.example/. Встреча завтра.

Выход содержит:

- `request.intent`: `prepare_materials`;
- `request.outputs`: `brief`, `presentation`;
- `institution_name`, `city`, `website_candidate`: фрагменты сообщения;
- `meeting_goal`, `meeting_date_text`, `template`: текст пользователя либо `null`;
- `next_step`: `resolve_institution` — серверу нужно определить учреждение;
- `run`: провайдер, модель, версия промпта и время запуска.

Название сохраняется в исходном падеже. Дата «завтра» сохраняется текстом: разрешать её
нужно с датой сообщения и часовым поясом пользователя. URL обозначает кандидат сайта;
его принадлежность учреждению пока не подтверждена. Адрес сам по себе не загружается.

## Решения после разбора

| `next_step` | Действие сервера/интерфейса |
|---|---|
| `clarify` | Показать `questions`; машинные причины находятся в `clarification_codes` |
| `resolve_institution` | Найти доступные карточки/кандидатов, уточнить неоднозначность, проверить сайт |
| `unsupported` | Сообщить, что запрос выходит за рамки этого первого шага |

Без названия или URL требуется `institution_required`. Один город недостаточен.
Если пользователь просит «материалы» без формата, требуется `output_required`.
Необязательные цель, дата и шаблон не блокируют поиск учреждения.
Запрос «Найди БГУ» не запускает генерацию: `find_institution` имеет пустой `outputs`.
Даже название с городом и URL всегда передаётся на разрешение организации;
интерпретатор не выдаёт ID и не утверждает, что личность организации установлена.

## Подключение в Python

```python
from app.services.llm import RequestInterpreter
from app.services.llm.client import GigaChatProvider, GigaChatSettings
from app.services.llm.requests import UserRequest

# Окружение загружает приложение; здесь нет неявного чтения .env.
interpreter = RequestInterpreter(GigaChatProvider(GigaChatSettings.from_env()))
result = await interpreter.interpret(UserRequest(message=user_message))
```

`UserRequest.schema_version="0.1"`; сообщение от 1 до 8000 символов после удаления
внешних пробелов, не более 2000 выделенных токенов (слова/знаки пунктуации).
Пустые и превышающие лимиты сообщения отклоняются до обращения к модели.
Модель выбирает диапазоны ID токенов, сервис копирует исходные срезы текста;
модель не формирует названия и URL заново. Сохраняются падежи, регистр и пробелы.
Неожиданные поля ответа, противоречия намерения/формата, неверные диапазоны
или URL дают `LLMError("invalid_request_interpretation")`.
Такая привязка не доказывает, что LLM верно поняла смысл или выбрала нужные слова;
распознавание намерения и границ сущностей требует отдельной оценки качества.
Коды ошибок провайдера сохраняются. Ошибка не заменяется успешным результатом.

## CLI и пример без API

Из `backend`:

```powershell
.venv/Scripts/python.exe -m app.services.llm interpret --input examples/llm/user_request.json --responses examples/llm/user_request_responses.json --output output/request-interpretation/offline.json
```

Этот пример воспроизводит сохранённый ответ для вымышленного колледжа. Для вызова
GigaChat убрать `--responses` и добавить `--env-file .env`:

```powershell
.venv/Scripts/python.exe -m app.services.llm interpret --env-file .env --input examples/llm/user_request.json --output output/request-interpretation/live.json
```

Код 0 означает успешный разбор, включая результат с уточняющим вопросом;
1 — неверный вход/конфигурация; 2 — отказ модели/проверки ответа.

## Границы текущей реализации

Нет HTTP-эндпоинта, истории сообщений, разрешения «его» из предыдущего сообщения,
применения ответа на уточнение, поиска карточек/сайтов, фоновых заданий или записи
в CRM. Сохранение контекста и объединение уточнений предстоит реализовать серверу.
Проверка источников и принятие фактов остаются отдельными этапами.
Интерпретатор не меняет статусы фактов и не создаёт файлы презентации.

Следующий шаг интеграции: сервер получает `resolve_institution`, ищет доступные
карточки и кандидатов, возвращает выбор при неоднозначности. Только после выбора
он использует существующую карточку либо начинает первичное исследование новой.

## Проверка прототипа 31.10.2026

Проходят 137 тестов общего LLM-модуля. Новые проверки покрывают уточнения,
отсутствующее учреждение, неоднозначную аббревиатуру, выход за границы токенов,
сохранение исходных форм слов и пробелов, запрет произвольных реквизитов и CLI.
Офлайн-тесты воспроизводят ответы; качество распознавания живой моделью они не измеряют.

В контрольном реальном вызове `GigaChat-2-Pro` с `interpret-request-v3` по
`examples/llm/user_request.json` получены оба формата, название «Северный», город N,
URL, цель и дата «завтра». Следующее действие — `resolve_institution`.
Модель выделила собственное имя без слова «колледже»: полноту границ названия нужно
учесть при дальнейшей оценке. Сырой ответ и результат сохранены локально в
игнорируемой папке `output/request-interpretation/`.

Предыдущие варианты промпта со свободными строковыми полями меняли падеж названия
и отклонялись проверкой. Итоговый контракт использует диапазоны токенов; проверки
привязки не ослаблялись. Это проверка работоспособности на одном вымышленном примере
с доработкой по результату, а не независимая оценка качества на новых запросах.
