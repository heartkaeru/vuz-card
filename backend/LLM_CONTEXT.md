# Профиль учреждения, проекты и события: контракт 0.3

Дата: 01.11.2026. Реализован отдельный режим LLM-извлечения и включение результатов
в справку/тезисы. Он работает с текстами парсера и не ищет страницы сам.
Контракты руководства/контактов 0.1 и 0.2 продолжают работать отдельно.
[Контроль прототипа, ошибки и ограничения](reports/llm_context_2026-11-01.md).

## Вход и поля

`AssistantPipeline.extract_facts(ContextExtractionRequest(...))` принимает
`schema_version="0.3"`, `institution` с ID/версией карточки, `documents` и необязательный
фильтр `fields` из `ContextField`. Документ содержит исходный `text`, URL, `source_id`,
даты загрузки/публикации и семантические `fragments`.

Фрагмент: `fragment_id`, `start`, `end`, необязательный `entity_scope_id`. Смещения —
индексы символов Python, `end` не включается. Фрагменты не пересекаются. Обычно одна
новость/карточка проекта передаётся одним фрагментом. Если заголовок и текст разделены,
парсер задаёт им общую область `entity_scope_id`: один проект/событие, а не весь сайт.

| Сущность | Поля |
|---|---|
| Учреждение | `institution.profile` |
| Проект | `project.name`, `project.program`, `project.role`, `project.status`, `project.period`, `project.description` |
| Событие | `event.name`, `event.type`, `event.date`, `event.status`, `event.description` |

Значения должны быть дословными. Неизвестные даты/роли не заполняются. Дата публикации
остаётся метаданными, не подставляется в `event.date`. Полные примеры строит
`examples/llm/context_demo.py`; ответы — в `examples/llm/extract_context_responses.json`.

## Доказательства и проверка

Модель возвращает название/вид сущности, ID опорного фрагмента с названием, поле,
значение и ID фрагментов доказательства. Сервис формирует `EntitySubject`, локальный
`entity_id`, точные цитаты, URL, хеш и смещения. Модель не назначает статус проверки.

Название и значение должны находиться в опорном фрагменте либо в общей области
`entity_scope_id`. Дата из соседней статьи не принимается даже при одинаковом названии
мероприятия. Разные области/документы и изменённые снимки автоматически не объединяются.
Различающиеся статусы/даты одной сущности в одном снимке отмечаются как `conflict`.
Это локальные ID упоминаний, не готовая система сопоставления проектов в БД.

Успешный факт остаётся `pending`, ошибочный — `rejected`. `complete` означает завершение
обработки переданных фрагментов и автоматических проверок, не полноту данных в интернете.
Пустой результат описывает отсутствие извлечённых фактов в переданном тексте, а не
отсутствие проектов у учреждения. Смысл и связь с учреждением проверяет сотрудник.

Ограничения вызовов берутся из `AssistantPipeline`: `chunk_size`, `max_chunks`.
Область сущности не разрывается между вызовами. Слишком большая область и превышение
лимита возвращаются как `context_scope_too_large` / `context_batch_limit_reached`.

## Генерация

Backend объединяет принятые факты руководства/контактов из 0.2 и контекста из 0.3 одной
карточки/версии в `GenerationRequest(schema_version="0.3", ...)`. Контакты сохраняют
владельцев; контекстные поля требуют подходящий `EntitySubject`. Обход через 0.1 запрещён.

Остаются требования: `verified`, автор/время принятия, проверка источника не старше
7 дней, `within_window`, отсутствие ошибок/конфликтов. Backend проверяет текущую версию
карточки до вызова — у LLM нет доступа к БД. Для контекстных фактов используется
`draft-context-v2`. Модели передаются выбранные значения и сущности, без длинных цитат
с непринятыми подробностями. Проверяются ID ссылок и новые числа.

Для контекстных утверждений сервис строит нейтральные строки из выбранных значений:
название, «Роль учреждения: …», «Статус проекта: …», «Дата события: …» и т. п.
Заголовки также формируются по виду сущности. Модель выбирает и упорядочивает факты;
её оценочные добавления («ключевой», «получил поддержку») в такие строки не переносятся.
Одно утверждение должно относиться к одной сущности; смешение разных сущностей или
контекстных/персональных фактов в одном утверждении отклоняется. Это не запрещает
разные разделы и отдельные утверждения о руководстве и проектах в одной справке.

Результат — `DraftResult(status="draft")`, JSON/Markdown с источниками. Смысловая
проверка текста остаётся обязательной: проверки цитат не доказывают, что модель верно
поняла участие в программе или статус события. Этот режим не выполняет матчинг продуктов
и не создаёт `.pptx`: генератор файлов должен использовать проверенный `draft.slides`.

## Пример и CLI

Из `backend`, без API:

```powershell
.venv/Scripts/python.exe -m examples.llm.context_demo
```

В `output/context-demo/` появятся `request.json`, `facts.json`, `reviewed_request.json`,
`draft.json`, `brief.md`. Учреждение и тексты вымышлены. Принятие для генерации
**имитируется только в примере**; оригинальные факты остаются `pending`, CRM не меняется.
Офлайн-пример не измеряет качество GigaChat.

Реальный вызов по данным парсера:

```powershell
.venv/Scripts/python.exe -m app.services.llm extract --env-file .env --input output/context-request.json --output output/context-facts.json
.venv/Scripts/python.exe -m app.services.llm draft --env-file .env --input output/reviewed-context-request.json --output output/context-draft.json --markdown output/context-brief.md
```

`reviewed-context-request.json` сервер формирует после настоящего принятия фактов.
Демонстрационную имитацию принятия нельзя переносить в рабочий процесс.

Нужна независимая оценка новых официальных материалов ВУЗ/СПО: проекты, планируемые
заявки, будущие/прошедшие события, чужие кейсы и неоднозначные даты. Эталон фиксируется
до вызова модели. Правильность смысловых связей оценивается отдельно от совпадения цитат.
