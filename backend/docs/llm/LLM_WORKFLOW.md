# LLM-модуль ВУЗ-CRM

Модуль извлекает факты из документов парсера, хранит их как кандидатов и готовит материалы по принятым сведениям. Рабочий путь проходит через `/api/v1/ai` и SQLite.

## Локальный запуск

Из корня репозитория:

```powershell
py -3.11 -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements-dev.txt
if (-not (Test-Path backend/.env)) { Copy-Item backend/.env.example backend/.env }
```

Создайте `backend/.env` из шаблона при первой настройке. Для GigaChat нужны `GIGACHAT_CREDENTIALS`, `GIGACHAT_MODEL` и `GIGACHAT_SCOPE`. `run.py` загружает этот файл, в CLI используется явный `--env-file .env`. При ошибке проверки сертификата настройте `GIGACHAT_CA_BUNDLE_FILE` по инструкции GigaChat. Для входа настройте `JWT_SECRET_KEY`. [Авторизация](../AUTH.md) · [Сертификаты GigaChat](https://developers.sber.ru/docs/ru/gigachat/certificates)

Запустите backend и frontend в отдельных терминалах из корня репозитория.

```powershell
Set-Location backend
.venv/Scripts/python.exe run.py
```

```powershell
Set-Location frontend
pnpm install --frozen-lockfile
pnpm dev
```

Интерфейс доступен на `http://127.0.0.1:3000`, Swagger — на `http://127.0.0.1:8000/docs`. Для отдельной SQLite используйте `run.py --db <путь>` из `backend`. Сбор выполняется в фоне FastAPI. После перезапуска прерванное задание помечается ошибкой и доступно для повторного запуска.

## Работа в интерфейсе

1. Войдите в чат. Из общего чата можно открыть сохранённый вуз или запустить первичный сбор: попросите создать карточку и укажите название; официальный URL необязателен, сервер найдёт его по названию. Город необязателен. Та же процедура работает из формы новой карточки. После создания откройте карточку: ход фонового задания и результат будут показаны там. В карточке можно указать точную страницу руководства, биографию и источники профиля. [PDF и предпросмотр](DOSSIER_PIPELINE.md#pdf-и-предпросмотр)
2. После сбора откройте «Проверить факты». Сверьте цитаты и источники, выберите отдельные поля или группу по человеку, подразделению либо другому объекту. Укажите проверяющего и основание. Принятие требует отметки о сверке источников. Замена дополнительно требует подтверждения архивирования прежнего значения.
3. В чате по карточке можно задать уточняющий вопрос и предложить правку рабочего телефона или почты. Перед записью агент показывает прежнее и новое значения. Подтверждение сохраняет решение и его автора в истории. У общего чата и чата по вузу разные истории.
4. При повторном сборе точное совпадение с надёжным свежим доказательством по ранее проверенному официальному URL обновляет дату сверки. Сохраняются ID факта и исходное решение сотрудника. Контекст включает владельца, подразделение и квалификаторы показателя. Новые значения, изменения и неоднозначные совпадения остаются в блоках сверки. Пропуск или ошибка сбора сохраняет прежние данные.
5. Укажите цель встречи, при необходимости подберите предложения. Запустите презентацию из карточки или чата. При просроченных выбранных фактах откройте «Повторная проверка перед экспортом». После завершения задания скачайте PPTX или DOCX и проверьте текст и источники. Справка доступна и в Markdown. [Варианты PPTX](../../templates/README.md)

## Контракты парсера и LLM

Для полного исследования нужен снимок `*_llm_card_*.json` с `UniversityData` и документами. Сводный `*_card.json` используется для других сценариев. Каждый документ содержит уникальный `source_id`, текст, URL и дату получения с часовым поясом. Фрагмент имеет ID и полуоткрытый диапазон Unicode `[start, end)` внутри текста после очистки. Фрагменты валидируются на пересечение и выход за границы текста. [Парсер](../../PARSER_README.md) · [Адаптер](../../parser/llm_adapter.py)

### Извлечение 0.2

Контракт покрывает ФИО, должности, подразделения, биографию и рабочие контакты. Модель возвращает атомарные значения и `fragment_ids`. Сервер сам сохраняет цитату `document.text[start:end]`, URL, даты, хеш и смещения.

- `contact_hints` связывает рабочий телефон или email с владельцем из разметки источника. `context_fragment_ids` может ссылаться на заголовок таблицы и область подразделения. `person` требует подтверждённой связи с ФИО. `office`, `department` и `organization` сохраняются как неперсональные контакты. При `unknown` факт требует уточнения.
- `biography_subject` связывает биографию с именным заголовком. `value_fragment_id` позволяет перенести длинное дословное значение. Подтверждение образования или карьеры не подтверждает текущую должность. Несколько кандидатов на должность руководителя требуют ручной сверки.
- Структурированные поля источника могут дать отдельный кандидат с доказательством даже при пропуске модели. Такой кандидат тоже проходит проверку и ожидает решения сотрудника. [Схема 0.2](../../app/services/llm/fragment_models.py)

### Извлечение 0.3

Профиль включает тип, местонахождение, дату основания, направления и уровни образования, численность и структуру. Для проектов и событий сохраняются роль, статус, сроки и описание при наличии в источнике. `entity_scope_id` связывает заголовок и текст одной публикации, `institution_anchor_id` связывает справочные абзацы с названным учреждением. Дата публикации хранится отдельно от даты события.

`institution.students` требует дословных `metric_context.period`, `scope`, `unit` и, если указан, `coverage`. Состав контингента, охват филиалов и период сверяются в источнике вместе со значением. Дата получения документа не подставляется вместо периода. Для численности из таблицы сотрудник сверяет строку, колонку и заголовки. [Схема 0.3](../../app/services/llm/context_models.py)

## Хранение и API

`AssistantPipeline` отвечает за модель и валидацию. `LLMWorkflow` и `LLMRepository` хранят исходный снимок, кандидатов, решения и факты, вошедшие в материал. `DemoRepository` добавляет черновые карточки `draft:`, задания и историю чатов. Черновой ID отделён от юридической идентичности в реестре. Версия карточки и ревизия исследования проверяются отдельно. [Workflow](../../app/services/llm/workflow.py) · [Хранилище](../../database/llm_store.py)

| Операция | Маршрут после `/api/v1/ai` |
| --- | --- |
| Полностью удалить карточку и связанные данные (требуется вход) | `DELETE /cards/{card_id}` |
| Создать карточку и запустить первичный сбор (сайт можно не указывать) | `POST /cards/intake` |
| Создать черновик без запуска сбора | `POST /cards` |
| Общий чат и запуск первичного сбора из диалога | `POST /chat/general` |
| Чат по вузу и подтверждение правки | `POST /cards/{card_id}/chat`, `POST /cards/{card_id}/chat/{turn_id}/confirm` |
| Актуализация и состояние задания | `POST /cards/{card_id}/refresh`, `GET /jobs/{job_id}` |
| Сравнение, принятие, сверка актуальности | `GET /runs/{run_id}/changes`, `POST /runs/{run_id}/reviews`, `POST /runs/{run_id}/recheck` |
| Подбор и формирование материалов | `POST /runs/{run_id}/partnership-matches`, `POST /runs/{run_id}/materials` |
| Выгрузка | `GET /materials/{material_id}/download?format=pptx` или `format=docx`, `GET /materials/{material_id}/brief` |

Чат использует JWT. Маршруты ручной сверки и принятия фактов сейчас принимают имя проверяющего из запроса. Генерация читает принятые факты из SQLite. Для выбранных фактов действует окно актуальности в 7 дней. Новые совпадения в истории помечаются `source_recheck`; запись исходного решения не изменяется. Принятие и замена проверяют текущую ревизию и сохраняются транзакционно. Повтор того же ключа с тем же входом возвращает существующее задание или исследование. Для повтора после сбоя нужен новый ключ. [Реализация API](../../app/api/v1/ai.py)

## Матчинг

Модель получает цель встречи, разрешённые позиции каталога и принятые факты о профиле, проектах и событиях. Она возвращает предложение, основание, вопрос к встрече и ID фактов. Сервер проверяет ссылки и подставляет название и URL из каталога. Предложения можно добавить в PPTX после просмотра.

Локальная матрица включает «Школу 21», стажировки Сбера, Академический центр СберУниверситета, кампусную карту, зарплатный проект, СберЗдоровье и внешний курс по визуализации данных. Для операционных продуктов требуется подтверждённая задача учреждения. Edutoria сохраняется как изученный кейс, а её подбор отключён до уточнения условий. Новости могут участвовать через принятые факты проектов и событий. Отдельный сбор новостей для этого сценария, интеграция со Study AI Agent, поиск нового учреждения по одному названию и мониторинг по расписанию остаются задачами развития. [Матрица и правила отбора](../../app/services/llm/partnership.py)

## CLI и офлайн-проверка

Из `backend`:

```powershell
.venv/Scripts/python.exe -m app.services.llm --help
.venv/Scripts/python.exe -m app.services.llm.workflow_cli --help
.venv/Scripts/python.exe -m examples.llm.workflow_demo
```

В автономном CLI доступен отдельный прототип `interpret` для разбора первого запроса. Общий чат использует `find_cards` и `collect_card` с серверной валидацией. `workflow_cli` выполняет `extract`, `show`, `review` и `draft` по сохранённому снимку. Подставные ответы включаются явно. Для интерфейса офлайн запустите `examples.llm.demo1_server` или `examples.llm.actualization_demo` вместо обычного backend. У каждого учебного примера своя база с вымышленными данными.
