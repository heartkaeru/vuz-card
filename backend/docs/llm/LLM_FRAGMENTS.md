# Извлечение по фрагментам: контракт 0.2

Новый режим устраняет повторный набор цитат моделью и явно хранит владельцев контактов.
Старый режим `0.1` остаётся доступным; его сценарии проверяются общим набором тестов.
Общие DTO получили дополнительные необязательные поля: строгие внешние потребители
должны согласовать обновление моделей. Это не автоматическая миграция CRM.

## Запуск

Установка и локальный ключ — по [основной инструкции](../../LLM_README.md).
Дополнительные библиотеки для самого режима не нужны.

Из `backend`, демонстрация на вымышленных данных без API:

```powershell
.venv/Scripts/python.exe -m app.services.llm extract --input examples/llm/extract_fragments_request.json --responses examples/llm/extract_fragments_responses.json --output output/fragments-demo.json
```

Тот же вход с реальным GigaChat:

```powershell
.venv/Scripts/python.exe -m app.services.llm extract --env-file .env --input examples/llm/extract_fragments_request.json --output output/fragments-live.json
```

CLI выбирает режим по `schema_version`. Для вызова из сервера:

```python
from app.services.llm.fragment_models import FragmentExtractionRequest

request = FragmentExtractionRequest.model_validate(parser_payload)
result = await pipeline.extract_facts(request)
```

## Что должен передать парсер

Организацию, её ID/версию и исходные документы с URL и датами, как в `0.1`.
В каждом документе дополнительно обязательны `fragments`:

- `fragment_id` — уникальный ID внутри этого документа;
- `start`, `end` — позиции Unicode-символов в неизменном `document.text`, конец не включается;
- `contact_hints` — необязательные структурированные контакты с областью владельца.

Смещения относятся к тексту после обработки HTML парсером, а не к байтам HTML-файла.
Фрагменты не должны пересекаться, выходить за текст или быть пустыми. Рекомендуемые
границы — карточка одного человека, заголовок таблицы, одна строка таблицы.
Один большой блок со многими людьми не даёт надёжного разделения владельцев.

`contact_hints` содержит `field` (`contact.email`/`contact.phone`), точное `value`,
`owner` и при необходимости `context_fragment_ids`. Контекст позволяет сослаться на
заголовки столбцов и ячейку подразделения, объединённую через `rowspan`.
Значение должно присутствовать в своём фрагменте, имя/название владельца — в нём или
его контексте. Формат контакта проверяется до запроса к модели.

Типы `owner.kind`:

| Тип | Смысл | `subject.person_name` в результате |
|---|---|---|
| `person` | Персональный рабочий контакт, явно связанный с полным ФИО | Это ФИО |
| `office` | Функциональный контакт должности, приёмной или канцелярии | `null` |
| `department` | Контакт подразделения | `null` |
| `organization` | Общий контакт учреждения | `null` |
| `unknown` | Владелец не установлен | Не принимается как определённый контакт |

Область определяется структурой и подписями источника, а не похожестью email на фамилию.
Например, контакт на странице ректора можно консервативно хранить как контакт должности
«Ректор», не утверждая, что он принадлежит исключительно конкретному человеку.
Это конфигурация разбора источника, которую сотрудник также должен проверить.

Метаданные области должен формировать доверенный серверный парсер. Проверка того,
что название встречается в тексте, не доказывает правильность семантического разбора
колонки. Не принимать `contact_hints` из браузера как уже подтверждённые сведения.
Данный модуль не реализует авторизацию и решение сотрудника CRM.

## Что возвращает модель и что делает сервис

Модель получает ID и тексты фрагментов. Она возвращает значение факта, субъект,
владельца контакта и `fragment_ids`. В схеме нет поля `quote`; ID ограничены
переданным набором. Неизвестные ссылки отклоняются и при локальной проверке.

Сервис строит доказательства сам:

```text
quote = document.text[start:end]
```

В результате сохраняются URL, даты, SHA-256 текста, `fragment_id`, `start_offset`
и `end_offset`. В отличие от проверки совпадения пересказанной цитаты, здесь модель
не может изменить букву внутри доказательства. Она всё ещё может выбрать неподходящий
фрагмент или неверно понять связь — поэтому ручная проверка сохраняется.

Значения копируются из фрагмента с проверкой границ слов: «ректор» не подтверждается
одним словом «проректор», а короткий email — частью другого адреса. Для ФИО сохранено
сопоставление словарных падежных форм. Имя и значение неконтактного факта должны
подтверждаться в одном семантическом фрагменте.

Для контакта дополнительно проверяется совпадение типа/названия владельца с областью
из парсера. Неизвестная область и противоречия остаются причиной отказа. Остаточное
ФИО в контакте приёмной тоже отклоняется, а не становится персональным контактом.

Инструкция `extract-fragments-v3` явно разделяет персональный контакт и контакт
приёмной/подразделения (`subject.person_name=null`). Контакты переносятся из
подсказок с точным владельцем и значением, включая добавочный номер. В 0.2 добавлено
необязательное поле фрагмента `subject_department`; старые входы без него поддерживаются.
Валидатор требует название в исходном фрагменте. Сервис заполняет пропущенную моделью
область человека из этой разметки, а противоречие областей отклоняет. Парсер, адаптер
и LLM-модуль обновляются вместе. Проверки цитат и принятие человеком сохранены.
Разметка microdata и [контроль на БГУ](../../reports/contact_quality_2026-11-04.md)
проверены вместе с парсером. [Перенос на БрГУ и АПЭТ](../../reports/contact_transfer_2026-11-04.md).
Эти контроли не являются общей оценкой точности.

Несколько одновременных ролей человека не считаются конфликтом только из-за разных
значений должности. Несколько кандидатов на единоличную должность ректора/директора,
включая и. о., помечаются для проверки.

## Прямой перенос структурированных контактов

Необязательный `project_structured_contacts=true` включает прямой перенос уже
выделенных парсером контактов с валидными значением и владельцем. По умолчанию он
выключен. Повторно извлекать такие значения нейросетью не требуется.

В серверном `LLMWorkflow` перенос включён явно для 0.2: пропущенный моделью
структурированный контакт сохраняется с `origin=parser_projection` и статусом
`pending`. Формат, дословность и область владельца проверяются контрактом;
неизвестный владелец и необработанные фрагменты не переносятся. Самостоятельные
вызовы библиотеки/адаптера по-прежнему требуют явного флага.

Происхождение кандидатов отмечается:

- `llm` — факт из ответа модели;
- `subject_projection` — отдельное ФИО из подтверждённого субъекта другого факта;
- `parser_projection` — контакт из структурированных данных парсера.

Повтор одного номера у того же подразделения не создаёт контакт для каждого сотрудника.
Для сравнения российских телефонов нормализуются оформление и префиксы 8/+7;
исходное значение сохраняется. Ошибки исходного ответа модели остаются в результате,
даже если корректный кандидат затем получен из структурированных данных.

Все кандидаты остаются `pending`, спорные — `conflict`, не прошедшие проверки —
`rejected`. Ни один из этих путей не присваивает `verified` автоматически.
`complete` относится к обработке, а не к полноте информации о вузе или принятию человеком.

## Справка с контактами

`GenerationRequest` для новых данных должен иметь `schema_version="0.2"`.
Генератор получает только принятые значения и владельцев; исходные цитаты остаются
в реестре источников. Контакты без владельца блокируются.

Утверждения, ссылающиеся только на контакты, сервис форматирует из точных значений
и названия владельца. Это сохраняет, например, «Учебная часть», вместо случайной
замены моделью на «учебный отдел». Смешанные утверждения с должностями, именами
и контактами по-прежнему требуют смысловой проверки сотрудником.

## Повторение сохранённого пилота

Понадобится `requirements-pilot.txt` и сохранённая локальная папка `output/pilot`.
Адаптеры ниже настроены только для трёх исследованных сайтов и не являются общим парсером:

```powershell
.venv/Scripts/python.exe -m examples.llm.prepare_fragment_pilot
.venv/Scripts/python.exe -u -m examples.llm.pilot extract --manifest output/pilot-v2/manifest.json
.venv/Scripts/python.exe -m examples.llm.evaluate output/pilot-v2
.venv/Scripts/python.exe -m examples.llm.evaluate output/pilot-v2 --gold contact-gold.json --output contact-metrics.json
```

`--replay` повторно обрабатывает сохранённые реальные ответы без нового запроса.
Такие результаты маркируются `provider=gigachat-recording`. Для генерации нужен
отдельный `reviewed-request.json`; в техническом примере принятие сотрудником CRM
явно имитировалось после сверки источников ассистентом и не обновляло рабочие карточки.

Результаты — в [отчёте версии 0.2](../../reports/llm_fragments_2026-10-31.md).

Первый прогон без изменения промпта на новых организациях — в
[отдельном отчёте](../../reports/llm_new_organizations_2026-10-31.md).
Сценарий диалогового запроса, включая учреждение вне базы, — в
[AGENT_WORKFLOW.md](../../../docs/proposals/AGENT_WORKFLOW.md); чат и поиск пока не реализованы.
