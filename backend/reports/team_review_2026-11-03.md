# Проверка парсера, БД и совместимости с LLM

Дата: 2026-11-03. Проверены `origin/main` на `8e112c8` и
`origin/database-excel-import` на `43384e4`. Исходная ветка пользователя:
`ai-llm`, `e7e8d74`. Проверка не вызывает GigaChat и не импортирует реальные
таблицы заказчика.

## Что сделала команда

**Парсер:** очистка HTML, профили четырёх вузов и поиск разделов сайта,
разбор таблиц руководства и контактов, проектов и новостей; документы с
фрагментами, JSON-экспорт, SQLite-хранилище документов, кэш, ограничения
обхода и адаптеры LLM-контрактов 0.2/0.3. Парсер уже включён в main.

**БД:** отдельная локальная SQLite-модель с учреждениями, юридическими лицами,
контактами и происхождением значений; таблицы встреч, договоров и ФОТ;
приём Excel в staging, явное подтверждение идентичности по mapping,
идемпотентное применение контактных данных и отчёты проверки. Из Excel
заполняется контактный реестр; наличие остальных таблиц не означает готовые
импорт или бизнес-процессы для них. На момент проверки ветка БД не включена в main.

Вместе с актуальной main получен демо-frontend. Его код в рамках этой проверки
не изменялся и отдельно не оценивался.

## Проверки исходных версий

- Backend с парсером: 187 тестов проходят.
- БД: 14 тестов unittest проходят. Эти тесты подменяют чтение Excel;
  они проверяют логику импорта, но не чтение настоящего XLSX через openpyxl.
- Дополнительно проверены настоящие Pydantic-контракты LLM на HTML-фикстурах,
  кэш после ошибки сети и импорт синтетического XLSX без подмены загрузчика.
- В исходной версии новые проверки воспроизвели ошибки ниже; одних исходных
  тестов было недостаточно для вывода о совместимости.

## Найденные и исправленные ошибки

| Проблема | Последствие | Исправление |
|---|---|---|
| Контакт без заголовка получает владельца «ВУЗ», отсутствующего в тексте | Весь документ отклоняет строгий контракт 0.2 | Контакт остаётся в исходном тексте; подсказка без подтверждённого владельца не создаётся |
| При отсутствии ректора адаптер берёт первого руководителя; проверка подстрокой принимает и «директор» | Проректор/директор попадает в `rector_fio` | Проверяется самостоятельное слово с формами «ректора»; без ректора возвращается `null` |
| Повторная очистка кэша присваивает сегодняшнюю `retrieved_at`, даже после timeout | Старые сведения выглядят недавно полученными для LLM | Сохраняется исходная дата загрузки HTML; использование кэша отмечается в метаданных |
| Весь документ получает один `entity_scope_id` | Статусы разных проектов допускается связывать; страницы длиннее лимита целиком пропускаются как oversized scope | По умолчанию фрагменты независимы; явно подтверждённые области можно передать на уровне фрагментов |
| Строка Excel `applied` с необработанным телефоном/ФИО не входит в очередь и может дать партии `completed` | Необходимая ручная проверка скрыта из CSV | В очередь включены применённые строки с открытыми замечаниями; добавлен счётчик `review_required` и корректный статус партии |

Исправления локальны для ветки пользователя; исходные коммиты команды
сохранены в истории. HTTP API, схемы CRM и генератор PPTX не переписывались.
Схема БД не менялась, миграция существующей базы не нужна.

Для 0.3 выбран консервативный режим: без явной разметки одной статьи связи
между разными абзацами могут не извлечься. Это видимое ограничение полноты;
семантическую группировку статей и карточек проектов ещё нужно развивать.

## Оценка готовности

Основа пригодна для дальнейшей локальной интеграции после перечисленных
исправлений. У БД уже есть полезные проверки целостности, происхождения,
идемпотентности и отказ от автоматического принятия неоднозначных учреждений.
У парсера есть управляемый обход и структурированные источники, но размер
реализации существенно больше покрытия тестами: 20 исходных дополнительных
тестов парсера не подтверждают качество всех профилей и эвристик.

Нельзя считать готовым общий MVP:

- FastAPI продолжает работать с mock-данными. Хранилище документов парсера
  и реестр CRM — отдельные базы, а не подключённый общий серверный процесс.
- Нет проверенного серверного адаптера записи кандидатов LLM в БД,
  ручного принятия через API и чтения принятой версии для генерации.
- Не согласовано преобразование UUID учреждений БД в текущие идентификаторы
  API и задач; нельзя подставлять значение `1` из примера адаптера всем вузам.
- БД создаёт подтверждённые карточки после ручного mapping с ИНН; для сценария
  нового учреждения без ИНН нужен отдельный путь исследования/черновика.
- Для проектов и событий пока нет выделенных бизнес-таблиц и согласованного
  преобразования фактов 0.3 в модель хранения.
- Приёмочные проверки должны включить сохранённые страницы реальных сайтов,
  ошибки/изменения структуры и реальный образец Excel. Качество поиска и
  извлечения на живых сайтах в этой проверке не измерялось.
- PDF/OCR, права доступа, optimistic locking и серверные задания требуют
  отдельной интеграции; локальные CLI не заменяют эти механизмы.

Следующий практический шаг — один сквозной сценарий на синтетическом учреждении:
HTML → документы парсера → кандидаты LLM → сохранение на проверку → решение
сотрудника → принятая версия → справка. Затем повторить на согласованном
наборе реальных источников с отдельной оценкой полноты и ошибок.
