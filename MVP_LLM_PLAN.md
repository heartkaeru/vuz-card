# MVP: работа Данила и зависимости от команды

Дата: 01.11.2026. Приоритет — первый этап из [README](README.md).
Это план LLM-части по роли Данила, а не заявление о готовности всего MVP.
Требования находятся в [спецификации](SPECIFICATION.md).

## Работа по роли AI / LLM Engineer

| Участок | Текущее состояние | Что осталось для MVP |
|---|---|---|
| Руководство и биография | Автономный модуль, есть пилоты официальных страниц | Подключение реального парсера к серверному заданию |
| Контакты и владельцы | Контракт 0.2, отделение персональных/общих контактов | Контекст владельцев от парсера, независимая проверка новых страниц |
| Профиль, проекты и события | Добавлен режим 0.3 и включение в справку/тезисы | Независимая оценка реальных материалов и смысловых связей |
| Справка и сценарий презентации | Генерация по принятым свежим фактам, JSON/Markdown с источниками | Серверное принятие и передача результата генератору `.pptx` |
| Возможности сотрудничества | Рабочего матчера пока нет | Проверенный каталог продуктов и гипотезы с основаниями из фактов |
| Изменения и актуальность | Давность перед генерацией, конфликты в извлечении | Сравнение с сохранёнными фактами и показ «было / предлагается» с backend |
| Разбор запроса пользователя | Прототип первого сообщения | Дополнительный сценарий, не заменяет основные функции MVP |

Ближайший порядок: контекстные факты → каталог/матчинг → независимая оценка → сквозной
запуск через API. Полный чат не должен откладывать проверку существующей карточки.

## Что необходимо узнать у команды сейчас

### Артём — парсер

Нужны функция/команда получения материалов и 2–3 реальных примера JSON:

- Руководство/контакты: [контракт 0.2](backend/LLM_FRAGMENTS.md), исходный текст,
  URL, `source_id`, дата загрузки, границы блоков, подтверждённая контекстом принадлежность контактов.
- Проекты/события: [контракт 0.3](backend/LLM_CONTEXT.md), одна статья/сущность в блоке
  либо общая `entity_scope_id` для заголовка и текста. Дата публикации — отдельно.
- Поддерживаемые форматы (HTML/PDF/сканы), возврат недоступных страниц и ошибок.
  Ошибка загрузки не должна превращаться в сообщение «проектов нет».
- Набор официальных URL для первого совместного прогона. Универсальный поиск по любому
  сайту не обязателен для первого соединения модулей.

### Дарья — backend и интеграция

Нужны точка вызова LLM и серверная модель принятия:

- Где worker передаёт `Institution(id, name, card_version)` и документы; готовые
  интерфейсы LLM — Python-функции/CLI, не новый HTTP-сервис.
- Куда сохраняются `ExtractionResult`, цитаты, пробелы и частичные ошибки.
  Текущий имитатор актуализации реальную LLM не вызывает.
- Какая операция принимает/отклоняет факты, разрешает конфликты и записывает автора
  из учётной записи сотрудника, время решения и проверки источника.
- Как фиксируются версия карточки и выбранные `fact_id`. Клиент не должен свободно
  назначать `verified` в JSON, обходя серверную проверку.
- Как `DraftResult.slides` и источники попадут в генератор файлов. Старый генератор
  использует mock-данные и путь `d:/Dev/…`; это ещё не экспорт проверенного LLM-результата.

### Максим — данные

Нужны актуальные схема/миграции и правила ID/версий:

- Как выдаётся ID вузу, колледжу, филиалу и новой черновой карточке.
- Где хранятся снимки, кандидаты, принятие/отклонение, `reviewed_by`, `reviewed_at`,
  `last_checked_at`, источники и история значений.
- Как хранятся проекты/события. Локальные `entity_id` из извлечения не должны
  автоматически объединять ежегодные события и сведения разных филиалов.

### Дарья / заказчик — каталог предложений для матчинга

Нужны таблица/JSON: ID и название продукта, описание, аудитория, условия/ограничения,
официальный источник, дата проверки. Названия из README задают направление, но не
доказывают актуальную доступность каждого продукта. Результат матчера — **гипотеза
для обсуждения**, основания (`fact_id` + продукт каталога) и вопросы, не факт партнёрства.

### Ангелина — интерфейс

После определения API нужны показ цитат/источников, действий принятия/отклонения,
конфликтов и давности; затем просмотр черновика справки/слайдов. Для проверки основного
сценария на существующей карточке полный чат не обязателен.

## Критерии готовности LLM-части MVP

1. Реальные материалы парсера проходят контракты; ошибки/пропуски видны.
2. Новые факты имеют точные доказательства и остаются кандидатами до решения человека.
3. Справка/тезисы опираются на принятые свежие факты одной версии; планы и даты
   не превращаются в неподтверждённые утверждения.
4. Гипотезы сотрудничества отделены от фактов и используют проверенный каталог.
5. Есть независимая разметка новых материалов и отчёт об ошибках, не только демонстрация.
6. Через сервер проверен путь «материалы → кандидаты → принятие → справка/тезисы»;
   генератор файлов использует именно этот результат и сохраняет источники.

Полный MVP дополнительно требует backend, парсера, БД, интерфейса, мониторинга и
экспорта. Успешные тесты LLM сами по себе эти пункты не закрывают.
