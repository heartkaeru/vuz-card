# Метрики проекта «Карточка ВУЗа»

Документ для защиты перед заказчиком: что измеряем, как считаем, какие значения получены
в пилоте и что из этого — оценка, а что — фактический замер.

Дата замеров: 26–27 ноября 2026. Ветка: `feature/auto-site-create`.
Скрипты и сырые данные: `docs/pilot_measurements.csv`, `backend/` (команды в разделе «Методика»).

---

## 1. Зачем эти метрики

Карточка ВУЗа заменяет ручной сбор данных о вузе: раньше сотрудник открывал сайт, искал
ректора, руководство, контакты, проекты и переносил всё в CRM. Метрики отвечают на три вопроса:

1. **Быстрее ли стало?** — время создания карточки.
2. **Полнее ли стало?** — сколько фактов и блоков заполняется автоматически.
3. **Можно ли этому верить?** — доля отклонённых кандидатов и доля сборов без ошибок.

## 4. Методика (как воспроизвести)

Замеры парсера (без LLM):

```bash
cd backend
python -m parser.main --name "<название вуза>" --with-official-site \
  --max-pages 1 --max-item-docs 0 --no-news-search
```

Замеры полного цикла — через API, как это делает интерфейс:

```bash
POST /api/v1/ai/cards            # создание по названию
POST /api/v1/ai/cards/{id}/refresh   # сбор + извлечение фактов
GET  /api/v1/ai/jobs/{job_id}        # completed_at - created_at
GET  /api/v1/ai/runs/{run_id}        # facts, errors, статусы
```

Правила подсчёта:

- **Время** — по `created_at`/`completed_at` задачи, без учёта ручных пауз.
- **Запись руководства** — валидное ФИО (2–3 слова, без служебных слов) и непустая должность.
- **Корректная должность** — без склейки строк (`|`) и без «хвоста» абзаца.
- **Отклонённый кандидат** — факт со статусом `rejected` после автопроверки доказательств.

## 5. Что является оценкой, а не замером

Честно помечаем, чтобы вопросы заказчика не застали врасплох:

| Величина | Статус | Обоснование |
|---|---|---|
| TTM «вручную» = 45 мин | **оценка** | 3 источника (сайт, агрегатор, контакты) + 100–300 записей руководства; подтверждается хронометражем 2–3 карточек |
| Экономия 82 % | **расчёт** | `1 − 8/45`; зависит от TTM «вручную» |
| Целевые значения (колонка «Цель») | **план** | взяты как «текущее + 10–20 %», достижимы без смены архитектуры |
| E2 «0–5 из 8» | **неполный замер** | режим профиля ещё доводится; после правки перезамерить |
| E3 «70–80 %» | **оценка** | по журналам ошибок формата GigaChat, точный подсчёт — на полной выборке |

## 6. Ограничения пилота

1. Выборка 10 вузов — не репрезентативна для всех ~1200 вузов РФ; часть сайтов может иметь
   нестандартную вёрстку.
2. Качество LLM зависит от GigaChat: модель периодически возвращает повреждённый JSON,
   поэтому статус сбора «частичный», а не «полный».
3. Полнота профиля (`institution.*`) и фото ректора — самые слабые места: 0/8 и 8/10.
4. **Лимит запросов GigaChat.** Несколько сборов подряд за короткое время дают
   `invalid_context_json` и 0 фактов. Для замеров делать паузу 1–2 минуты между прогонами;
   при защите показывать заранее сохранённую карточку, а не запускать сбор в зале.

---

## 6.1. Как отвечать на вопрос «откуда цифры»

- **Время, записи, контакты, ошибки** — из журналов задач и файлов карточек
  (`created_at`/`completed_at`, `card.leadership`, `card.contacts`, `card.errors`).
  Любую цифру можно пересчитать командой из §4.
- **10/10 по сайту и ректору** — сверяли вручную: сайт с официальным доменом, ректор с
  официальной страницы вуза.
- **Экономия времени** — расчёт от экспертной оценки ручного сбора (40–50 мин),
  формула в A3, а не «магическое число».
- **Цели** — плановые, не факт. В презентации отделять «получено» от «план».
